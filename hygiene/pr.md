# PR descriptions

- **Lead with the experience, not the implementation.** Describe the user-visible change or the problem solved. Skip "wraps X", "centralizes Y", "adds helper Z", and don't sell the approach or call out what it avoids ("no fake entries", "no X churn", "without touching Y") — the diff shows the mechanics. Don't cite commit, file, or line counts ("70 commits", "3 files changed"); the commit list and diffstat already show them.
- Open with the motivation (link the source), then state the resulting behavior change. No headers needed for short PRs.
- **No test plan section** unless the PR adds verification work beyond what CI runs automatically. Do not enumerate `make test`, `go vet`, `npm test`, etc., and do not defer verification to the reviewer in prose ("the major bumps still need runtime testing", "validate before merge") — CI is the verification authority. If you do mention a manual check, do it first and report the outcome; never leave it as an open box.
- **No follow-up / next-steps section** unless those follow-ups exist as filed issues to link to. Conversation-only ideas (e.g. "we should also do X later") belong nowhere on the PR.
- **No reviewer hand-holding.** Don't add a "Reviewer Instructions" or how-to-review section — what's safe to drop, how the commits are organized, what to focus on — or manual-verification checklists for the reviewer, unless the change genuinely cannot be CI-verified.
- **Skip empty template scaffolding.** When the repo PR template lists sections like "Reviewer Instructions" or "Checklist", include them only when you have substantive, actionable content. Omit the section rather than reproduce an empty or all-unchecked version, even though the template lists it.
